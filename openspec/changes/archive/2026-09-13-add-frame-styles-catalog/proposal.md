## Why

The frame feature has grown from one style to two (`classic`, `gallery`) by hand-writing a bespoke branch per style across every switch in `WhiteFrameRenderer` (mat fill, caption resolution, drawing). The user wants to keep adding new frame looks over time (starting with two concrete ones now, a flat-mat two-column style and a centered "shot on" style, with more to follow in later requests) — at that rate, each addition re-paying the full "new branch everywhere" cost does not scale, and it risks each style's code drifting from the others in ways that are hard to keep consistent. This change identifies what is actually shared between styles — how the mat is filled, how a caption is laid out — and factors those into small, reusable pieces, so a new style is normally "pick a fill, pick a layout, supply field defaults" rather than a fresh bespoke render path.

## What Changes

- **Mat fill becomes a shared, reusable choice.** Today `gallery`'s vertical gradient fill is drawn inline inside `drawFrame`'s style switch, entangled with that one style. This factors mat fill into a flat-color option (already what `classic` does) and the existing gradient option, so any style can pick either without duplicating drawing code.
- **A second reusable caption layout: centered, multiple lines.** `classic` already draws one centered line; this generalizes that drawing path to take an ordered list of lines instead of exactly one, each line independently styleable (weight/color), which both `classic` (unchanged, still one line) and the new `print` style (two lines) can use. `gallery`'s two-column layout is unchanged and continues to be reused as-is by any style built on it.
- **One new technical capability the mockups require: mixed-weight text within a single line.** The credit line reads "Shot on **iPhone 15 Pro Max**" — a regular lead-in and a bold device-model run on one line. No current style needs more than one weight per line; this adds that as a small, reusable drawing primitive rather than a one-style special case.
- **Two new concrete styles, built from the above:**
  - ~~`slate`~~ — **dropped during implementation.** It was to be `gallery` with a flat mat, and it turned out to differ from `gallery` in nothing else at all. A style that duplicates another style's every behaviour to change one fill is a second picker entry saying the same thing twice, so the gradient became an on/off setting *on* `gallery` instead. Same two looks, one less style, and the flat tone is the one the graduated mat already reached at the caption so nothing needed retuning.
  - ~~`studio`~~ — **dropped after review.** It was a flat-mat uniform border with a centred two-line credit caption, and side by side with `classic` it turned out to differ only in splitting the same caption across two lines. That is not a style, it is a line break. Its credit caption survives on `print`, which is where the two-line treatment earns its space.
- **A third style, `print`.** The photo is lifted off a plain flat mat by a drop shadow, with the user choosing whether it falls downwards (resting on the mat) or evenly on all sides (floating above it). Its depth is derived from the mat, like the keyline, rather than being another control. It carries the centred two-line credit caption — "Shot on **{device model}**" as a fixed, non-configurable first line, then the resolved manufacturer name followed by the user's selected metadata fields, joined with plain spacing rather than `classic`'s "·" separator — set larger and with a taller band than `classic`'s. The manufacturer name is resolved the same way `gallery`'s brand mark already is (metadata-driven, not user-chosen); when none resolves, the name is simply omitted, the same way `gallery` omits its mark. It offers no keyline — the shadow already does that job, and together they fight.
- **Style picker becomes a dropdown.** A segmented control divides its width between its options, so each new style made every label narrower; at four they truncated. A menu costs one tap, stays legible at any number of styles, and has room to show each style's summary beside its name. The entries themselves are already driven by `FrameStyle.allCases`; the work is in the settings rows below, which branched on a single `if style == .classic { … } else { … }` where the else arm meant "gallery". That binary branch is now driven by what a style's caption layout actually is.
- **A fourth style, `banner`.** A full-bleed photograph over a caption bar: no mat on three sides, the maker's mark and a fixed "Captured with" credit at the far left of the bar, the shooting values over the equipment at the far right, all set in capitals with a little tracking. It is the first style whose export is *not* larger than the source in both dimensions, which is the one assumption in the geometry that had to be relaxed for it.
- **Not a plugin system.** Styles stay a closed, exhaustive enum (`FrameStyle`), not a registered/dynamic list — Swift's exhaustive `switch` is what already catches a style left unhandled somewhere, and that safety net is worth keeping rather than trading away for open-ended extensibility nobody asked for. "Easier to add" means smaller diffs per style, not a plugin architecture.

## Capabilities

### Modified Capabilities
- `photo-frames`: adds two new frame styles (`print`, `banner`), makes `gallery`'s gradient a setting rather than a second style, and generalizes the style system's internal building blocks (mat fill, centered-caption layout) so they compose across styles instead of being drawn bespoke per style. No existing style's behavior changes: `classic` and `gallery` render exactly as they do today.

## Impact

- **Rendering** — `WhiteFrameRenderer.swift`: extract the flat-vs-gradient mat fill into a shared helper; generalize the centered single-line caption drawing into a centered multi-line drawing helper (adding mixed-weight run support for one line); add the `print` branch built from those pieces plus the shadow, which is applied to the finished mat in Core Image after the platform branch (design.md D9); add `banner`'s two-block bar, which shares the mark sizing and the lens-name trim with `gallery` rather than restating them.
- **Models** — `WhiteFrameConfig.swift`: add `print` and `banner` to `FrameStyle` plus a `gradientEnabled` flag and a `shadow` choice; `print` reuses the existing `captionFields` for its second line rather than adding new configurable slots — no new caption-slot properties needed. Decoding stays backward-compatible: an older saved template naming none of these is unaffected, per `FrameStyle`'s existing lenient-decode fallback to `classic`.
- **Brand resolution** — reuses `BrandMarkRegistry`'s existing manufacturer normalization (already used to pick `gallery`'s mark) to resolve the credit caption's manufacturer name text, adding a display-name lookup where a brand key does not simply capitalize correctly (e.g. "dji" → "DJI", "oneplus" → "OnePlus").
- **UI** — `WhiteFrameToggleView.swift`: the `classic`-vs-else settings branch becomes layout-driven; `print` shows the same field-selection rows `classic` already has and none of `gallery`'s slot/mark rows, while `banner` takes the field rows *and* the mark rows — which is what finally made the binary branch untenable, since it is neither style's row set. The caption-prefix row is the one row that does not simply follow `classic` for `print` — see design.md D6.
- **Preview freshness** — `previewIdentifier` already includes the style's raw value, so switching style retriggers the preview today; the new styles add no new config fields. This is a confirm-only step, and it has to be confirmed in **both** implementations: `App/ViewModels/WatermarkViewModel.swift` and `ShareExtension/ShareExtensionViewModel.swift`.
- **Tests** — `WhiteFrameRendererTests` and `FrameStyleConfigTests` gain `print` and gradient cases. Note there are no frame snapshot baselines committed today: `__Snapshots__` holds only share-extension images, so the "compare against existing baselines" safety net for the refactor has to be built rather than reused — see design.md D1 for what is a throwaway local check and what is a committed test.
- **Future styles**: this change is explicitly the first of several — more frame mockups are expected in follow-up requests. It does not attempt to anticipate what they need; a genuinely new layout still gets its own new code when it arrives. Two of the three styles proposed here were dropped for being settings rather than styles, which is the bar a future one has to clear.
- **Ordering** — this change modifies the `photo-frames` requirement "Frame style selection", which currently exists only inside the still-unarchived `add-frame-styles` change; `openspec/specs/` is empty. Archive `add-frame-styles` before archiving this one, or the modification has no baseline to apply against.
