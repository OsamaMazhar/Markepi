## Why

The frame feature has grown from one style to two (`classic`, `gallery`) by hand-writing a bespoke branch per style across every switch in `WhiteFrameRenderer` (mat fill, caption resolution, drawing). The user wants to keep adding new frame looks over time (starting with two concrete ones now, a flat-mat two-column style and a centered "shot on" style, with more to follow in later requests) — at that rate, each addition re-paying the full "new branch everywhere" cost does not scale, and it risks each style's code drifting from the others in ways that are hard to keep consistent. This change identifies what is actually shared between styles — how the mat is filled, how a caption is laid out — and factors those into small, reusable pieces, so a new style is normally "pick a fill, pick a layout, supply field defaults" rather than a fresh bespoke render path.

## What Changes

- **Mat fill becomes a shared, reusable choice.** Today `gallery`'s vertical gradient fill is drawn inline inside `drawFrame`'s style switch, entangled with that one style. This factors mat fill into a flat-color option (already what `classic` does) and the existing gradient option, so any style can pick either without duplicating drawing code.
- **A second reusable caption layout: centered, multiple lines.** `classic` already draws one centered line; this generalizes that drawing path to take an ordered list of lines instead of exactly one, each line independently styleable (weight/color), which both `classic` (unchanged, still one line) and the new `studio` style (two lines) can use. `gallery`'s two-column layout is unchanged and continues to be reused as-is by any style built on it.
- **One new technical capability the mockups require: mixed-weight text within a single line.** The `studio` style's first line reads "Shot on **iPhone 15 Pro Max** Apple" — a regular prefix, a bold device-model run, and a regular manufacturer-name suffix, all on one line. No current style needs more than one weight per line; this adds that as a small, reusable drawing primitive rather than a `studio`-only special case.
- **Two new concrete styles, built from the above:**
  - `slate` (working name): `gallery`'s existing two-column caption, geometry and brand-mark logic, unchanged — with the mat fill switched from the gradient to a flat color. This is the "no gradient" look requested first.
  - `studio` (working name): a uniform flat-color border on all sides (no gradient), with a centered two-line caption — "Shot on **{device model}** {manufacturer name}" as a fixed, non-configurable first line (mirroring how `classic`'s layout is not slot-configurable either), and a second line built from the user's selected metadata fields (reusing the existing field-selection mechanism `classic` already offers, joined with plain spacing rather than `classic`'s "·" separator, matching the reference layout). The manufacturer name is resolved the same way `gallery`'s brand mark already is (metadata-driven, not user-chosen); when no manufacturer resolves, the first line simply omits the trailing name, the same way `gallery` omits its mark.
- **Style picker gains two entries.** `WhiteFrameToggleView` offers `slate` and `studio` alongside `classic` and `gallery`, each showing only the settings rows relevant to it. The picker itself is already driven by `FrameStyle.allCases`, so the entries appear for free; the work is in the settings rows below it, which today branch on a single `if style == .classic { … } else { … }` where the else arm means "gallery". That binary branch has to become style-driven, because `studio` needs the classic arm and `slate` needs the gallery arm.
- **Not a plugin system.** Styles stay a closed, exhaustive enum (`FrameStyle`), not a registered/dynamic list — Swift's exhaustive `switch` is what already catches a style left unhandled somewhere, and that safety net is worth keeping rather than trading away for open-ended extensibility nobody asked for. "Easier to add" means smaller diffs per style, not a plugin architecture.

## Capabilities

### Modified Capabilities
- `photo-frames`: adds two new frame styles (`slate`, `studio`) and generalizes the style system's internal building blocks (mat fill, centered-caption layout) so they compose across styles instead of being drawn bespoke per style. No existing style's behavior changes: `classic` and `gallery` render exactly as they do today.

## Impact

- **Rendering** — `WhiteFrameRenderer.swift`: extract the flat-vs-gradient mat fill into a shared helper; generalize the centered single-line caption drawing into a centered multi-line drawing helper (adding mixed-weight run support for one line); add `slate` and `studio` branches built from these pieces plus `gallery`'s existing two-column drawing (reused, not duplicated, for `slate`).
- **Models** — `WhiteFrameConfig.swift`: add `slate` and `studio` to `FrameStyle`; `studio` reuses the existing `captionPrefix`/`captionFields` fields for its second line rather than adding new configurable slots — no new caption-slot properties needed. Decoding stays backward-compatible: an older saved template naming neither style is unaffected, per `FrameStyle`'s existing lenient-decode fallback to `classic`.
- **Brand resolution** — reuses `BrandMarkRegistry`'s existing manufacturer normalization (already used to pick `gallery`'s mark) to resolve `studio`'s manufacturer name text, adding a display-name lookup where a brand key does not simply capitalize correctly (e.g. "dji" → "DJI", "oneplus" → "OnePlus").
- **UI** — `WhiteFrameToggleView.swift`: the `classic`-vs-else settings branch becomes style-driven; `studio` shows the same field-selection rows `classic` already has, none of `gallery`'s slot/mark rows, and `slate` shows `gallery`'s. The caption-prefix row is the one row that does not simply follow `classic` for `studio` — see design.md D6.
- **Preview freshness** — `previewIdentifier` already includes the style's raw value, so switching style retriggers the preview today; the new styles add no new config fields. This is a confirm-only step, and it has to be confirmed in **both** implementations: `App/ViewModels/WatermarkViewModel.swift` and `ShareExtension/ShareExtensionViewModel.swift`.
- **Tests** — `WhiteFrameRendererTests` and `FrameStyleConfigTests` gain `slate` and `studio` cases. Note there are no frame snapshot baselines committed today: `__Snapshots__` holds only share-extension images, so the "compare against existing baselines" safety net for the refactor has to be built rather than reused — see design.md D1 for what is a throwaway local check and what is a committed test.
- **Future styles**: this change is explicitly the first of several — more frame mockups are expected in follow-up requests. It does not attempt to anticipate what they need beyond what `slate` and `studio` already require; a genuinely new layout still gets its own new code when it arrives.
- **Ordering** — this change modifies the `photo-frames` requirement "Frame style selection", which currently exists only inside the still-unarchived `add-frame-styles` change; `openspec/specs/` is empty. Archive `add-frame-styles` before archiving this one, or the modification has no baseline to apply against.
