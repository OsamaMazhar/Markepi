## Context

See proposal.md (Why) and `tools/softbinding-probe/HANDOFF.md` for the full evidence. This design references the handoff's sections as §N.

Current state that shapes the approach:

- **Photo export path.** `WatermarkEngine.processImage` renders a `CIImage` composite, calls `context.createCGImage(… format: renderFormat …)`, then `ImageWriter.write`. The render format is RGBA8 or RGBAh: 16-bit is used for deep or wide sources. Signing comes after: `C2PAProvenanceClient.signExport(outputURL:source:manifest:identity:)` attaches a manifest to the written file and reads it back (`verification.signatureIsIntact`).
- **Unused hooks from the planning phase.** `C2PAManifestRequest.invisibleWatermarkPayloadID` exists but is always `nil` (WatermarkEngine.swift:358). It is already written into `c2pa.markepi.provenance` when set. `ExportReceipt.invisibleWatermarkApplied: Bool` already exists.
- **Gain maps.** These ride separately as `gainMapAuxData` aligned by `GainMapProcessor`. The base `CGImage` is the SDR rendition, so the watermark touches the base only and HDR is untouched by construction. This has to be proven by a test, not assumed.
- **Share Extension.** It is a handoff bridge: it saves to the App Group inbox and opens the app. It never exports, so keeping the ML out of it needs no new mechanism, only no linkage of the models into its bundle.
- **Project files.** The project uses classic `project.pbxproj` file references. New `.swift` files inside the `MarkepiCore` SPM target are picked up automatically, but app-target resources (the models) and app-target Swift files need manual pbxproj entries.
- **Tests.** Package tests run on macOS with `swift test`. Core ML exists on macOS, so the encoder, decoder, codec, PDQ and registry are all testable there.

## Goals / Non-Goals

**Goals:**
- Embed TrustMark P with a 61-bit Markepi payload in signed photo exports, with bounded memory at any resolution.
- Bind it into the C2PA manifest the way Adobe's reference flow does: watermark, then sign, then read back.
- Give users a Verify screen that is honest about what each piece of evidence means.
- Keep everything on-device.

**Non-Goals:**
- Video, a cloud resolver, CAI trust-list enrolment, and the QR/DataMatrix channel (§10).
- Recovering from crops above 10 %, which P cannot do (§7.2). The fingerprint and the honest wording cover the gap; switching to variant Q is a separate decision.
- Verifying exports made on another device beyond what their embedded manifest says.
- Pro gating changes. The watermark has exactly the availability of Content Credentials signing; changing that is a separate change.

## Decisions

### D1. TrustMark P over Q, WAM or InvisMark
P gives 48–50 dB, is on the C2PA soft-binding list as `com.adobe.trustmark.P`, and is MIT including the weights (§4).
- **Q** covers the whole frame but costs 3–5 dB. Its centre-square advantage was never measured head-to-head (§14), so it is not worth the quality loss yet.
- **WAM** is 32 bits and too CPU-heavy at 256².
- **InvisMark** has little independent replication.

The cost of P is that it only marks the centre square (§8.1). That is accepted because the fingerprint (D7) and the honest wording carry it.

### D2. Core ML, not MLX or ONNX Runtime
The encoder ships as fp32 (17.3 MB) and the decoder as int8 linear (23.9 MB). The decoder matched PyTorch with sign agreement 1.0000 and passed 6/8 attacks, the same as baseline (§7.5).
- **MLX** has no port and would take about a day of work for no gain (§7.6).
- **ONNX Runtime** adds a third-party dependency and around 15 MB of runtime, against the no-third-party-libs rule.
- **6-bit palettization** was rejected because it dropped to 5/8 attacks.

The models are generated by `tools/softbinding-probe/scripts/coreml_p2.py`. They are committed under `App/Resources/TrustMark/` as `.mlpackage`, and Xcode compiles them to `.mlmodelc` at build time.

**Placement.** The models live in the app target only, never in `MarkepiCore`'s resources, because the package is linked into the Share Extension. `MarkepiCore` takes model URLs through injection. Tests load the same `.mlpackage` files via `#filePath` and `MLModel.compileModel(at:)`.

### D3. Provider boundary in MarkepiCore
`MarkepiCore/Provenance/InvisibleWatermark/` holds:
- `protocol InvisibleWatermarkProvider: Sendable` with `embed(into: CIImage, payload: WatermarkPayload) async throws -> CIImage` and `decode(from: CGImageSource) async -> DecodedWatermark?`;
- `TrustMarkPProvider`, the Core ML implementation;
- `NoopInvisibleWatermarkProvider`, used for the Share Extension, unit tests and builds without models.

The provider is injected through `ProvenanceExportOptions` (new field `invisibleWatermark: (any InvisibleWatermarkProvider)?`). This mirrors how `c2paClient` is injected, so the engine never hard-codes a model path.

### D4. Composite in the CIImage graph, not a hand-rolled strip compositor
The handoff's strip-tiled compositor (§12) solves a problem Core Image already solves: CI renders tiled, so a full-frame float residual never exists in memory. The flow is:

1. **Encoder input.** Crop the composite to its centre square, scale it to 256² with Lanczos, and render that small image to an RGBA8 buffer in sRGB. Then run the encoder to get a 256²×3 residual in [−1, 1].
2. **Residual image.** Wrap the residual as a small RGBAf `CIImage` and multiply by 0.5. That is the ×127.5/255 conversion from encoder units to normalised pixel units (§13 trap 2). Scale it with bilinear sampling to the centre-square size and translate it to the square's origin. Strip mapping in global coordinates (§13 trap 3) comes for free from the affine transform.
3. **Add.** Apply the residual in gamma-encoded sRGB units, which is what the model was trained on:
   - convert the base from the working space with `CILinearToSRGBToneCurve`;
   - add the residual with a minimal CI colour kernel (`base.rgb + res.rgb`, `base.a` kept, clamped to [0, 1] for 8-bit output);
   - convert back with `CISRGBToneCurveToLinear`.
4. **Render.** `createCGImage` runs as today, in either format.

The colour kernel is chosen over `CIAdditionCompositing` because additive compositing mishandles alpha and signed values in this pipeline (see memory note *ci-additive-compositing-alpha-pitfalls*). The kernel is three lines.

**Large images.** When `min(W, H) > 4096`, nothing extra is needed: the residual is always generated at 256² and upsampled, which already matches the handoff's 4096² proxy rule.

**Alternative rejected: a Swift port of `lean2.py`'s strip loop on raw buffers.** It would be more code, separate 8-bit and 16-bit paths, and duplicated colour-space handling.

The strength is fixed at effective 1.25, never scaled down with resolution (§8.3).

### D5. Payload codec
Bits are laid out MSB-first: namespace `0x4D` (8), random asset ID (32), CRC-16/CCITT-FALSE over namespace and ID (16), and epoch (5). The epoch is days since 2026-01-01 divided by 128, modulo 32. Encoding uses BCH_5 in binary mode, never text mode (§13 trap 5).

The ID comes from `SystemRandomNumberGenerator` and is re-rolled if it is already in the local registry. Collisions across devices are possible in a 32-bit space, which is why the Verify screen confirms by fingerprint (D7) and never by ID alone.

`DecodedWatermark` is returned only when the namespace and CRC validate. The decoder's `present` flag is never trusted on its own (§8.2).

The soft-binding `value` is `"1*<61-bit string>"`, following Adobe's `<encoding>*<bits>` convention (§10).

### D6. Pipeline order in `WatermarkEngine.processImage`
The new steps are marked ★.
1. Render the composite (existing).
2. ★ If explicit signing is on, a creator is set, the watermark toggle is on, a provider is injected, and the output is JPEG or HEIC: generate the payload and set `composited = try await provider.embed(into: composited, payload:)`.
3. `createCGImage` and `ImageWriter.write` (existing, gain map unchanged).
4. ★ Compute the PDQ hash of the written file from a ≤512 px thumbnail.
5. Sign (existing), with `invisibleWatermarkPayloadID` set. `buildManifestJSON` adds the `c2pa.soft-binding` assertion and appends `{"action": "c2pa.watermarked"}` when the ID is present.
6. ★ Self-check: decode from the signed file, compare the IDs, and set the receipt status.
7. ★ Write the registry entry (D8) with the manifest JSON from `verifyExport` / `C2PA.readFile`.

Steps 4, 6 and 7 are best-effort: a failure there never fails the export. Embedding errors in step 2 downgrade to "not applied" plus a receipt warning; they don't throw. Throwing is reserved for explicit signing failures, as today.

`ExportReceipt.invisibleWatermarkApplied: Bool` is replaced by `invisibleWatermark: InvisibleWatermarkStatus` (`.embedded`, `.embeddedUnverified`, `.notApplied`). The receipt is Codable, so decoding keeps backward compatibility by mapping the old Bool key.

### D7. PDQ fingerprint, ported to Swift
Meta's PDQ (BSD) is the de-facto perceptual hash for this kind of matching and is what the handoff pairs with TrustMark (§8.6). The pipeline is:
- luminance;
- downscale to 512 px;
- a Jarosz tent filter down to 64×64;
- a 16×16 DCT;
- median threshold, giving a 256-bit hash with a 0–100 quality score.

It is about 250 lines of Swift with vDSP for the DCT, in `MarkepiCore/Provenance/InvisibleWatermark/PDQ.swift`. Correctness is pinned to the reference implementation's published test vectors. A C++ target was rejected because MarkepiCore has no C/C++ targets and Swift–C++ interop adds build friction for both app targets.

**Match threshold.** A Hamming distance ≤ 31 confirms a match, which is Meta's recommended starting point. It is calibrated in task 3.5 against WhatsApp-style re-encodes and against unrelated images. A hash with a quality score below 50 never confirms a match.

### D8. Local registry
The registry lives in `Application Support/Markepi/Credentials/`. Each export gets one `<id-hex>.json` holding the ID, the epoch, the export date, the PDQ hash (hex), and the manifest JSON read back from the signed file. Each also gets a 256 px HEIC thumbnail, `<id-hex>.heic`.

- **App sandbox, not the App Group.** Only the app writes or reads it.
- **Included in device backup.** The user expects their record to survive a phone restore.
- **No database.** Lookup is a file-exists check by ID. The count shown in Settings is a directory listing.
- **"Clear Credentials Records"** in Settings deletes the folder.

### D9. Verify screen
`App/Views/Verify/VerifyView.swift` is a new app-target file and needs a pbxproj entry. Its view model lives in `MarkepiCore/UI/` so it is unit-testable. The pipeline is:

1. **Input.**
   - **Photo library:** `PhotosPicker` with `preferredItemEncoding: .current`, loading a custom `Transferable` with a `FileRepresentation(importedContentType: .image)`. This gets the original bytes, because `Data` and `Image` representations can transcode and drop JUMBF.
   - **Files:** `.fileImporter` with security-scoped access.
   - Both copy into a temp file that is deleted on dismiss.
2. **C2PA.** `C2PA.readFile(at:)` through a new `C2PAProvenanceClient.inspect(at:) -> C2PAInspection?` that returns the generator, signer, creator, date, actions, ingredient presence, `signatureIsIntact`, `modifiedAfterSigning` (from hard-binding status codes), and `isTrusted` (false when `signingCredential.untrusted` is present). It extends the existing parsing in `parseVerification` and `parseManifestSummary`.
3. **Watermark.** `provider.decode`.
4. **Registry and PDQ.** Look up the decoded ID, compute the PDQ hash of the input, and take the Hamming distance.
5. **Verdict.** A pure function `VerifyVerdict.make(inspection:watermark:match:)` maps the evidence to exactly one headline from the spec. It is table-tested over every combination.

**Entry points.** "Verify a Photo" is a `NavigationLink` in the Settings Content Credentials section (ContentView.swift around line 1199). On the home screen, a toolbar button (SF Symbol `checkmark.seal`) presents the same view.

**Copy rules.** No "verified", "authentic" or "fake". A self-signed identity reads as "Unrecognized signer (Markepi device identity)".

### D10. Setting
`WatermarkConfiguration.includeInvisibleWatermark: Bool` defaults to `true`. It is shown under the Content Credentials toggle in `ProvenanceControlsView`, only while `includeC2PAManifest` is on, with the footer "Hides a tiny ID in the pixels so copies shared without metadata can still be matched to this export on your iPhone." It must be mirrored in `previewIdentifier` only if it ever affects previews, which it doesn't (previews are never watermarked). That is noted in code so a future change doesn't miss it.

## Risks / Trade-offs

- **[Device numbers are macOS-only (§14).]** Mitigation: task group 1 is a go/no-go device spike, run before integration, that measures memory and time on a 4 GB device plus Core ML parity on device. If the int8 decoder or ANE path deviates, fall back to an fp16 decoder (47.5 MB).
- **[The CI-graph composite might not match the probe's PIL output.]** Bilinear upsampling, tone-curve conversion and clamping could all differ. Mitigation: the robustness tests (task 3.4) run the Swift embedder through the same attacks as `wmtest_p.py`, and the go/no-go bar is the same 6/8.
- **[Centre-square-only coverage means wide crops or reframes lose the ID.]** Mitigation: crops up to 10 % per side still decode (§7.2). Beyond that the Verify screen falls back to "No Content Credentials found", never anything negative. A head-to-head with Q is listed as a follow-up.
- **[Watermark IDs are forgeable (WmForger).]** Mitigation: a match is never trusted without the fingerprint. The headline for an unconfirmed match is "Watermark matches, but the image content differs".
- **[PhotosPicker may hand over a transcoded file and drop the manifest.]** Mitigation: `.current` encoding plus a `FileRepresentation`. Task 5.2 tests the path on device with a signed export saved to Photos. If Photos itself strips JUMBF on save, the screen still works through the watermark and registry, and the copy says so.
- **[App size grows by about 41 MB.]** Accepted. On-demand resources were considered and rejected: verification must work offline on first use.
- **[HDR could be flattened if the base is not purely SDR in some path, such as RGBAh for 10-bit HEIC.]** Mitigation: task 3.3 is an HDR gate. Exporting a real HDR photo must keep the gain map (exiftool plus `CGImageSourceCopyAuxiliaryDataInfoAtIndex`), render HDR, and decode. Per the never-compromise-HDR rule, if a conflict appears the watermark is skipped for that export ("not applied", with a warning); HDR is never dropped.
- **[The registry grows without bound.]** About 30 KB per export (the thumbnail plus the manifest JSON). That is negligible, and Clear is available.

## Migration Plan

- **Additive.** The new receipt enum decodes old receipts. Manifests without an ID are byte-identical to today's.
- **Rollback.** Ship the toggle default as a build constant (`InvisibleWatermarkDefaults.enabledByDefault`). If a field issue appears, a point release can flip the default off or inject `NoopInvisibleWatermarkProvider`. Exports already made stay valid C2PA files either way.
- **Before archive.** Update `AGENTS.md` (the share-extension rule, and the models living in the app target only) and the C2PA memory notes. Store copy must not claim proof of authorship or video watermarking.

## Open Questions

- Whether to add a `markepi verify <file>` CLI subcommand for QA. It reuses the same view model, so it's cheap, but it's optional (task 6.4).
