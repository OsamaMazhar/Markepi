    The script is a thin wrapper — it delegates all complex logic to GSD tooling. Do NOT reimplement frontmatter parsing or regex mutation.

    **Implementation contract:**

    1. **Shebang + strict mode:** `#!/usr/bin/env bash` followed by `set -euo pipefail`

    2. **Argument validation (D-02):** Accept exactly one argument: the SUMMARY path. If missing or file doesn't exist, print error to stderr and exit 2.

    3. **Frontmatter extraction:** Call `gsd-sdk query frontmatter get "$SUMMARY_PATH" --pick requirements-completed`. Handle three cases:
       - JSON array with IDs (e.g., `["TRACE-01","TRACE-02"]`) → proceed
       - `null` or empty string → exit 0 (no requirements to process; not an error)
       - Empty array `[]` → exit 0 (plan delivered no new requirements)

    4. **JSON parsing:** Use `jq -r '.[]'` as primary parser, piped through `paste -sd, -` to produce comma-joined string. Provide a `node -e` fallback if `jq` is unavailable (check via `command -v jq`).

    5. **Delegation to mark-complete:** Pass the comma-joined IDs to `gsd-sdk query requirements mark-complete <comma-joined-ids>`. Capture both stdout (JSON result) and stderr. Print the JSON result to stdout.

    6. **Error detection (D-09 — CRITICAL):** `mark-complete` returns JSON with `not_found` array but exits 0 even when not_found is non-empty. The script MUST parse the JSON response via `jq -r '.not_found | length'` and exit 1 if length > 0. Print each not_found ID to stderr with the prefix "BLOCKER:".

    7. **Exit code contract:**
       - Exit 0: All IDs marked_complete or already_complete, no not_found. Safe.
       - Exit 1: At least one ID in not_found. Plan-completion BLOCKER (D-09/D-10).
       - Exit 2: Script error (missing SUMMARY, invalid frontmatter, tool failure). BLOCKER.

    8. **Output:** Print the `mark-complete` JSON result to stdout at minimum. On not_found, print blocker message + IDs to stderr before exit 1.

    **Concrete identifiers:**
    - `gsd-sdk query frontmatter get "$SUMMARY_PATH" --pick requirements-completed` (frontmatter extraction)
    - `gsd-sdk query requirements mark-complete "$COMMA_IDS"` (mutation delegation)
    - `jq -r '.not_found | length'` (error detection)
    - All error output goes to `>&2` (stderr)
    - Normal output goes to stdout

    **Pattern reference:** The RESEARCH.md lines 450-489 and PATTERNS.md lines 22-103 contain near-complete implementation code. Follow those patterns exactly — they were derived from live testing against the actual tooling.

    After creating the file, make it executable: `chmod +x scripts/sync-requirements.sh`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|-----------|-------------|
| SUMMARY.md frontmatter → sync-requirements.sh | The script reads `requirements-completed` from SUMMARY frontmatter. Source is the gsd-executor (trusted), not external input. |
| sync-requirements.sh → gsd-tools (frontmatter/mark-complete) | The script delegates to GSD tooling via CLI. No direct file mutation by the script itself. |
| sync-requirements.sh → .planning/REQUIREMENTS.md | Mutation happens exclusively through `mark-complete` (Node.js regex in milestone.cjs), not through bash text processing. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-04 | Tampering | sync-requirements.sh — shell injection via frontmatter values | mitigate | The script never uses `eval` on extracted JSON values. `jq` parses JSON safely with proper string quoting. The `requirements-completed` array values are piped through `jq -r '.[]'` which outputs plain strings. Comma-joined strings are passed as a CLI argument to `mark-complete`, not interpolated into shell expressions. Requirement IDs follow the `[A-Z]+-\d+` pattern enforced by GSD templates. |
| T-08-05 | Tampering | sync-requirements.sh — silent failure on not_found (recreating v1.0 drift) | mitigate | The script parses `mark-complete`'s JSON response and checks `.not_found.length > 0`. Exits 1 when non-empty. This is the most critical threat — RESEARCH.md Pitfall #1 documents that `mark-complete` exits 0 even when `not_found` is populated. The fixture test (Task 2, Fixture 2) explicitly validates this branch. |
| T-08-06 | Information Disclosure | test-sync-requirements.sh — temp directory leak | mitigate | `trap 'rm -rf "$TESTDIR"' EXIT` ensures cleanup on both pass and failure paths (Pitfall #4). `mktemp -d` creates the temp dir in `$TMPDIR` (outside the workspace). No secrets, PII, or production data in test fixtures — only synthetic TEST-A01/TEST-B99 IDs. |
| T-08-07 | Tampering | test-sync-requirements.sh — fixture pollution of real REQUIREMENTS.md | mitigate | The test `cd`s into `$TESTDIR` before running `mark-complete`. The GSD tooling's `planningPaths(cwd)` resolves `.planning/REQUIREMENTS.md` relative to `cwd`. By running from a temp directory, the test isolates mutations to the temp fixture files. The real `.planning/REQUIREMENTS.md` is never touched. |
| T-08-08 | Elevation of Privilege | sync-requirements.sh — path traversal via SUMMARY arg | accept | The SUMMARY path is provided by the gsd-executor (trusted), not from user input. The script validates that the argument is a file that exists (`-f`). No path traversal risk — the executor always passes a well-formed path to a plan SUMMARY within `.planning/phases/`. |
| T-08-09 | Denial of Service | sync-requirements.sh — resource exhaustion | accept | The script performs at most 2 lightweight CLI calls (frontmatter get + mark-complete). No loops, no recursion, no network I/O. No DoS vector from synthesized SUMMARY content. |
</threat_model>
