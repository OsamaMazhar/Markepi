      **Revised implementation approach (simpler, per D-01/D-02):**
      - Step 1: Watermark the still frame: load still image from `stillImageURL`, apply `buildFilterGraph()`, render to `CGImage`, write to temp still output URL.
      - Step 2: Watermark the video component: use `WatermarkEngine.shared.processVideo(sourceURL: videoURL, config: config)` — the existing video watermarking pipeline applies the CALayer overlay. The video output is a watermarked MOV.
      - Step 3: Re-assemble as Live Photo: use `PHLivePhotoEditingContext` if we can construct one from the watermarked pair. If not available, return the watermarked still + watermarked video as a `ProcessingResult` with a `.livePhotoPair` marker so the ViewModel presents them together.
      
      **Actually, the cleanest approach per RESEARCH.md Pattern 2:**
      Since we can't easily construct `PHLivePhotoEditingContext` from raw URLs, we use a two-phase approach:
      - Phase A: Watermark still image → temp still URL
      - Phase B: Watermark video via existing VideoProcessor → temp video URL  
      - Phase C: Return a `ProcessingResult` with both URLs marked as a Live Photo pair. The ViewModel shares them as a pair.

      For `PHLivePhotoEditingContext.frameProcessor` usage (the documented approach), we'd need the user to import via the Photos extension (PHContentEditingController) which already provides `PHContentEditingInput`. For the main app's PhotosPicker import, the two-phase approach is correct.

      **Final implementation:**
      ```swift
      public struct LivePhotoProcessor {
          public struct LivePhotoPairResult {
              public let watermarkedStillURL: URL
              public let watermarkedVideoURL: URL
              public let stillOutputUTI: String
          }
          
          public static func process(
              stillImageURL: URL,
              videoURL: URL,
              config: WatermarkConfiguration
          ) async throws -> LivePhotoPairResult {
              // 1. Watermark still frame
              let stillResult = try await WatermarkEngine.shared.process(
                  sourceURL: stillImageURL,
                  config: config
              )
              // 2. Watermark video frames
              let videoResult = try await WatermarkEngine.shared.processVideo(
                  sourceURL: videoURL,
                  config: config
              )
              // 3. Return paired result
              return LivePhotoPairResult(
                  watermarkedStillURL: stillResult.url!,
                  watermarkedVideoURL: videoResult.url!,
                  stillOutputUTI: stillResult.outputUTI
              )
          }
      }
      ```
      
      This is the pragmatic approach: watermark each component individually using the existing engine pipeline, then return the pair. The output is two watermarked files (still + video). When shared, both files represent the watermarked Live Photo pair.
      
      Per Pitfall 2 (RESEARCH.md): if either processing step fails, throw the error. The ViewModel catches it and falls back to still-only watermarking with a user alert.
